# YOBI 챗봇 시스템 차후 개선 방향

- 최초 작성일: 2026-08-09 KST
- 최신 개정일: 2026-08-09 KST
- 기준 브랜치: `codex/master-spec-completion`
- 기준 배포 카탈로그: `demo-2026.08.08-chat-menu-v1`
- 최상위 제품 명세: `YOBI_FINAL_MVP_CODEX_MASTER_PROMPT.md`
- 문서 목적: 현재 챗봇의 실제 동작과 한계를 정리하고, 자연스러운 다중 턴 대화와 **YOBI 메뉴 지식 그래프 기반 하이브리드 추천·설명 시스템**을 구현하기 위한 공통 기준을 제공한다.

이 문서는 기존 Master Spec을 대체하지 않는다. 제품 범위와 안전 원칙은 Master Spec을 따르며, 이 문서는 특히 **자연스러운 다중 턴 대화, 사용자 니즈 수집, 추천 타이밍, 추천 품질**을 개선하기 위한 후속 방향을 다룬다.

## 1. 결론

현재 YOBI는 Oracle 검색, 식이 제약 필터, 근거 카드, 서버 장바구니, Mock 결제·주문 등 보존할 가치가 있는 기반을 갖추고 있다. 그러나 사용자가 기대하는 다음 핵심 경험은 사실상 미구현에 가깝다.

> 여러 차례의 자연스러운 대화를 통해 사용자의 식사 니즈를 충분히 파악하고, 추천할 준비가 되었을 때만 누적된 맥락을 근거로 타당한 메뉴를 제안한다.

현재 문제는 단순한 LLM 말투나 프롬프트 품질 문제가 아니다. 대화 상태, 니즈 슬롯, 추천 준비도, 부정 조건, 후보 거절 이력, 카드 선택 결과를 관리하는 **대화 오케스트레이션 계층 자체가 부족하다.** 따라서 프롬프트나 모델만 교체해서는 해결되지 않는다.

추천·설명 품질도 단순히 리뷰 수나 Vector 검색 비중을 늘리는 방식으로 해결할 수 없다. 차후 YOBI는 다음 구조를 목표로 한다.

> 사람이 검토 가능한 음식 Wiki를 기반으로 재사용 가능한 음식 개념과 핵심 재료 지식을 만들고, 이를 가게별 원산지·메뉴·옵션 근거와 결합한다. 서버의 규칙 엔진이 제약과 안전성을 판정하고, LLM은 누적 대화 상태와 동일한 판정 결과를 사용해 자연스럽게 질문·추천·설명한다.

핵심 책임은 다음처럼 분리한다.

- 대화 상태 엔진: 사용자가 무엇을 원하는지와 추천할 준비가 되었는지 판단
- SQL과 규칙 엔진: 실제 주문 가능한 후보 및 하드 제약 판정
- 음식 Wiki·지식 그래프: 음식 설명, 관계, 일반적인 핵심 재료와 변형 지식 제공
- 가게·메뉴·옵션 근거: 일반 지식을 실제 판매 메뉴 수준에서 보강하거나 수정
- Vector Search: 자연어와 관련 있는 음식 개념 및 설명 passage 검색
- LLM: 질문, 요약, 비교, 설명 등 사용자 경험 담당

## 2. 현재 시스템을 쉽게 설명하면

현재 자유 대화의 기본 흐름은 다음과 같다.

```text
사용자 메시지
→ 마지막 문장의 키워드로 도구 3~4개 선택
→ LLM 호출
→ 필요 시 Oracle/Repository 도구 실행
→ LLM 문장과 도구 결과 카드 생성
→ 도구 결과나 카드가 없으면 오류 처리
→ deterministic fallback
```

구현상 중요한 특징은 다음과 같다.

1. 프로필, 현재 세션 상태, 최근 메시지 5개가 LLM에 전달된다.
2. 도구 선택은 세션 상태가 아니라 마지막 사용자 문장의 키워드를 중심으로 결정된다.
3. LLM이 인사나 명확화 질문처럼 도구 없이 답하면 정상 대화로 인정되지 않는다.
4. 도구 결과나 카드가 없으면 `GENAI_GROUNDING_REQUIRED`로 처리된다.
5. fallback이 아는 소수의 고정 시나리오에 해당하지 않으면 무조건 메뉴 검색과 카드 추천으로 이어진다.
6. 메뉴 선택 후 옵션·주소·결제 진행은 챗봇의 대화 상태가 아니라 프론트엔드 `OrderFlowPanel`이 주도한다.
7. 사용자가 고른 메뉴는 브라우저 `sessionStorage`에는 저장되지만 챗봇의 서버 대화 상태에는 반영되지 않는다.

이 구조에서는 `hi`, `아직 모르겠어`, `질문부터 해줘`, `내가 말한 걸 요약해줘` 같은 발화를 대화 행위로 처리하기 어렵다. 정상적인 명확화 응답도 카드가 없다는 이유로 실패 처리될 수 있다.

| 국물은 싫으며 더 필요한 정보를 물어보라 | 칼국수·돼지국밥 추천 | 부정 조건 처리 실패 |

| 두 번째 메뉴 카드를 설명해 달라 | 데이터에 없는 상세 재료·위험 정보를 장문으로 생성 | 이전 카드 참조와 사실성 검증 부족 |
| 돼지고기 제외인데 왜 돼지국밥을 보여줬는지 지적 | 돼지국밥과 탕수육 세트를 다시 추천 | 정정·오류 회복 실패 |

이번 단일 세션의 9개 진단 메시지 중 7개가 화면상 `Demo continuity mode` fallback으로 처리됐다. 이는 전체 운영 실패율을 의미하지는 않지만, fallback이 자연스러운 대화를 보존하지 못한다는 사실은 명확히 보여준다.

특정 조건이 충분히 구체적인 경우 LLM 정상 경로도 동작했다. 따라서 LLM 연결이 완전히 중단된 상태는 아니다. 다만 정상 경로에서도 다음 문제가 확인됐다.

- 본문에서 추천한 메뉴와 카드 후보가 일치하지 않음
- 데이터에 없는 재료와 위험 정보를 사실처럼 생성
- 근거보다 강한 식이·알레르기 표현 사용
- 사용자에게 불필요한 내부 메뉴 ID와 근거 ID 노출
- 프론트엔드가 Markdown을 렌더링하지 않는데 Markdown 표와 강조 문법 출력
- YOBI 내부 주문 흐름 대신 외부 배달 플랫폼에서 메뉴 ID를 참조하라는 부적절한 안내

각 fallback의 정확한 서버 예외 원인은 외부 화면만으로는 확인할 수 없다. 현재 코드는 provider 오류, rate limit, 잘못된 도구 인자, 빈 응답, 무도구 응답 등을 사용자 화면에서 하나의 fallback 결과로 합친다.

## 4. 구현 상태 판정

### 4.1 실제로 구현된 기반

- OCI GenAI Responses API 및 Function Calling 반복 루프
- 허용된 14개 도구와 Pydantic 입력 검증
- Oracle SQL 및 `VECTOR_DISTANCE` 검색
- 가격·맵기·일부 알레르기·비건 하드 필터
- `VERIFIED`, `RISK_SIGNAL`, `UNKNOWN`, `CONFLICTING` 근거 모델
- 근거·메뉴·비교·옵션 카드
- 서버 장바구니 계산과 재검증
- Mock 결제·주문 및 idempotency
- 주소 확인과 OCR
- 감사 로그와 deterministic fallback

이 영역은 단순 화면 껍데기가 아니며, 차후 개선 시 보존해야 한다.

### 4.2 부분 구현됐지만 품질이 낮은 영역

- 짧고 일반적인 시스템 프롬프트
- 최근 메시지 5개에 의존하는 제한적인 문맥
- 키워드 기반 도구 라우터
- LLM 본문과 카드의 일관성 검증 부재
- LLM 최종 문장의 사실성·근거 검증 부재
- 실제 리뷰·지식 근거 내용이 부족한 tool result
- deterministic semantic-hash 기반 검색
- 템플릿 중심 합성 데이터
- 예외 원인별 관측 가능성 부족

### 4.3 사실상 미구현인 핵심 대화 기능

- 인사·잡담·명확화·요약·정정·거절·선택 의도 분류
- 대화 중 확보한 식사 니즈의 구조화 저장
- 아직 부족한 정보 추적
- 추천할 준비가 되었는지 판단하는 readiness gate
- `no soup`, `not noodles` 같은 부정 조건 저장과 적용
- 이미 보여준 후보와 사용자가 거절한 후보 기억
- `두 번째 메뉴`, `아까 추천한 메뉴` 같은 지시 대상 해석
- 상태 전이 규칙과 허용 행동 제어
- 프론트엔드 카드 선택을 서버 대화 상태에 반영
- 대화 행위를 보존하는 상태별 fallback
- 실제 다중 턴 대화 품질 평가

DB에는 `state_stack_json`, `required_slots_json` 컬럼이 있지만 세션 생성 시 초기값을 넣은 뒤 실제 대화에서 읽거나 갱신하지 않는다. `Session` 도메인 모델에도 이 정보가 포함되지 않는다. 즉 상태 머신의 스키마 흔적은 있으나 동작하는 대화 상태 엔진은 아니다.

## 5. 코드상 핵심 원인

### 5.1 명확화 질문을 실패로 처리하는 계약

LLM 결과에 도구 실행 내역이나 카드가 없으면 `GENAI_GROUNDING_REQUIRED`가 발생한다. 따라서 다음과 같은 정상 답변이 실패 처리될 수 있다.

```text
Hi! What kind of meal are you in the mood for?
```

안전한 일반 대화와 근거가 필요한 메뉴 사실 응답을 구분해야 한다.

### 5.2 모든 일반 fallback이 추천으로 수렴

고정된 rain/vegan/kalguksu/tteokbokki/compare 패턴에 해당하지 않으면 fallback은 마지막 사용자 문장을 그대로 검색해 메뉴 3개를 반환한다. 추천 준비도와 사용자 의도는 검사하지 않는다.

### 5.3 구조화된 니즈 상태가 없음

현재 서버가 기억하는 주요 값은 대략 다음뿐이다.

- 프로필의 식이 규칙·맵기·좋아하는 음식
- 세션의 큰 상태 이름
- 선택 메뉴·가게 ID 일부
- 최근 메시지 5개

식사 형태, 온도, 식감, 포만감, 예산, 인원, 긍정·부정 조건, 거절 후보 등은 구조화되어 누적되지 않는다.

### 5.4 도구 스키마와 실제 검색 계약 불일치

카테고리 추천 도구는 다음 인자를 받는다.

- `servings`
- `desired_temperature`
- `desired_texture`
- `desired_flavors`

하지만 현재 `ToolRegistry`는 이 값을 검증만 한 뒤 실제 Repository 검색에는 전달하지 않는다. 풍부한 도구 스키마가 존재하지만 백엔드 추천 로직이 이를 사용하지 않는 상태다.

### 5.5 부정 조건과 제외 재료 처리 부족

- `no soup`도 embedding과 keyword boost에서는 `soup`의 긍정 신호가 될 수 있다.
- `excluded_ingredients`는 Repository에서 사실상 돼지고기만 특수 처리한다.
- 그마저 현재 seed에는 `pork` 태그가 하나도 없어 돼지국밥과 탕수육 세트를 제외하지 못한다.
- 주소를 채팅 전에 확인하지만 메뉴 검색에서 배달 서비스 지역 필터로 사용하지 않는다.

### 5.6 대화 UI와 서버 상태의 단절

- 카드 전체는 브라우저 `sessionStorage`에 보관된다.
- 서버에는 assistant 본문 텍스트만 저장된다.
- 카드 후보 순서와 근거는 다음 LLM 턴에서 재사용할 수 없다.
- `Choose this menu`는 프론트엔드 상태만 갱신하며 서버 챗봇에 선택 이벤트를 전달하지 않는다.

따라서 챗봇은 사용자가 실제 화면에서 무엇을 보고 선택했는지 안정적으로 알 수 없다.

### 5.7 현재 평가가 대화 품질을 측정하지 않음

기존 타깃 테스트와 100-query 평가는 현재 코드에서 통과한다. 하지만 100-query 평가는 `hello` 같은 입력도 챗봇이 아니라 `repository.search_menus()`에 직접 전달한다. 검증 대상은 주로 가격·맵기·근거 존재 여부이며, 다음 항목은 측정하지 않는다.

- 추천 타이밍
- 질문의 적절성
- 다중 턴 맥락 유지
- 정정과 거절 반영
- 본문과 카드 일관성
- 대화 자연스러움
- fallback 적절성

현재 테스트 통과는 검색·주문 기반의 회귀 증거이지 챗봇 품질 증거가 아니다.

## 6. 데이터와 RAG 현황

### 6.1 현재 seed 품질

현재 코드의 합성 seed를 분석하면 다음과 같다.

| 항목 | 전체 | 고유 내용 |
|---|---:|---:|
| 메뉴 | 150 | 영어 메뉴명 110종 |
| 메뉴 설명 | 150 | 34종 |
| 문화 설명 | 150 | 34종 |
| 리뷰 | 600 | 8종 |
| 근거 문구 | 300 | 8종 |

추가로 근거 300개 중 284개가 `UNKNOWN`이며, 각 메뉴의 정규화된 ingredient 연결은 실제 재료가 아니라 메뉴 카테고리 1개 수준이다.

따라서 단순히 메뉴·리뷰 개수를 늘리는 것만으로는 추천 품질이 향상되지 않는다. 템플릿 복제가 늘어나면 Vector Search의 구별력만 더 낮아질 수 있다.

### 6.2 현재 RAG의 실질적 수준

현재 구현은 완성된 RAG보다는 **Vector 기반 후보 랭킹**에 가깝다.

- 메뉴·리뷰·knowledge 벡터 거리를 계산한다.
- SQL 하드 필터와 벡터 점수를 함께 사용한다.
- 그러나 일반 메뉴 추천 시 LLM에 실제 리뷰·knowledge 근거 문장이 충분히 전달되지 않는다.
- tool result에는 근거 ID와 요약 위험 신호가 중심이고, 상세 재료 데이터가 부족하다.
- 라이브 임베딩은 실제 의미 임베딩 모델이 아닌 deterministic semantic hash다.
- 리뷰와 근거 원문 자체가 소수 템플릿 반복이다.

따라서 실제 RAG 개선은 데이터 계약과 근거 품질 개선 이후에 진행해야 한다.

### 6.3 리뷰와 가게 설명의 차후 역할

실제 서비스에서 리뷰는 짧고 반복적이거나 상업적일 수 있으며, 현재 합성 리뷰도 고유 문장 8개가 반복된다. 데모 단계에서는 리뷰를 핵심 추천과 안전 판정에서 제외한다.

- `review_similarity` 가중치는 `0`으로 둔다.
- 리뷰 passage를 추천용 LLM 컨텍스트에 넣지 않는다.
- 리뷰로 재료 부재, 알레르기 안전, 비건·할랄 적합성을 판정하지 않는다.
- 기존 `REVIEW_SNIPPET` 테이블과 데이터는 삭제하지 않고 보존한다.
- 차후 품질이 검증된 경우에만 체감 맵기, 양, 포장, 배달 후 식감 같은 약한 신호로 제한적으로 재도입한다.

가게 설명도 마케팅 문구 자체는 낮은 신뢰도로 취급한다. 다만 영업 상태, 배달 가능 지역, 가격, 최소 주문액, ETA와 같은 구조화된 운영 정보는 주문 가능성을 결정하는 필수 하드 조건으로 계속 사용한다.

### 6.4 원산지 정보의 가치와 한계

요기요의 가게별 `원산지 정보`와 유사한 합성 필드를 목업 DB에 추가한다. 원산지 정보는 가게가 특정 재료를 사용한다는 사실과, 메뉴명이 명시된 경우 해당 메뉴의 재료 사용을 확인하는 강한 양성 근거다.

그러나 원산지 정보는 모든 소스·양념·부재료·가공품·알레르기 유발물질의 완전한 목록이 아니다. 따라서 다음 원칙을 적용한다.

- 기재된 재료의 존재는 해당 범위에서 강한 근거로 사용한다.
- 기재되지 않았다는 사실만으로 재료 부재를 판정하지 않는다.
- 가게 전체 범위의 원산지 정보는 모든 메뉴에 자동 전파하지 않는다.
- 특정 메뉴명이 함께 명시된 경우에만 `MENU_INGREDIENT`의 메뉴별 사실로 승격한다.
- 교차접촉, 인증, 조리도구 공유 여부는 별도 근거로 관리한다.
- 런타임마다 LLM이 원문을 다시 해석하지 않고, seed/ingestion 단계에서 정규화하고 검증한다.

## 7. 목표 시스템: YOBI 메뉴 지식 그래프 기반 하이브리드 추천·설명 시스템

### 7.1 한 줄 정의

> YOBI는 고품질 음식 Wiki의 핵심 재료를 실제 메뉴의 기본값으로 상속해 선제적으로 필터링하고, 가게·메뉴·원산지·옵션 정보를 이용해 그 기본값을 보강하거나 수정한다. 단, 일반 지식에 재료가 없다는 사실만으로 안전을 보증하지 않는다.

이 시스템은 `문서 RAG`, `관계형 DB`, `지식 그래프`, `규칙 기반 판정`, `대화 상태 엔진`을 역할에 맞게 결합한다. 어느 하나가 다른 계층을 대신하지 않는다.

### 7.2 Markdown Wiki와 Oracle DB의 결합

Markdown과 DB 중 하나를 선택하지 않는다. 사람이 편집하는 원본과 런타임 정본을 분리한다.

```text
음식별 Markdown 원본
→ 스키마·출처·관계 검증
→ 음식 개념·재료 주장·설명 문서로 정규화
→ 설명 facet별 chunk 생성
→ embedding 생성
→ Oracle 관계형·Vector 테이블 적재
→ 추천·안전 판정·음식 설명에서 공동 사용
```

제안하는 Markdown 원본 경로 예시는 `knowledge/dishes/<cuisine>/<family>/<variant>.md`다. 이 파일은 아직 구현된 경로가 아니라 차후 authoring 계약이다.

Markdown에는 다음 정보를 충분히 상세하게 작성한다.

- 음식의 정의, 기원, 문화적 배경
- 맛, 향, 식감, 온도, 포만감, 일반적인 양
- 비슷한 음식과 차이
- 외국인에게 설명할 때 유용한 비유
- 대표 재료와 각 재료의 역할
- 소스·육수·가공품을 통한 간접 재료
- 자주 존재하는 변형과 옵션
- 알레르기·식단·종교상 주의 가능성
- 출처, 검토 상태, 버전, 마지막 갱신일

DB에는 Markdown 전문을 `CLOB`로 보존하고, 판정에 필요한 주장은 구조화한다. 음식 설명 품질은 파일 확장자가 아니라 지식 내용, 구조, 검색, 출처 품질에 좌우된다. 같은 Markdown 내용을 DB에 적재하면 Wiki 수준의 상세 설명을 유지하면서 정확한 SQL 필터와 근거 추적을 추가할 수 있다.

### 7.3 권장 논리 데이터 모델

기존 테이블을 보존하면서 다음 논리 구조를 추가하거나 확장한다.

| 논리 테이블 | 역할 |
|---|---|
| `DISH_CONCEPT` | 김밥, 참치김밥, 짜장면 같은 재사용 가능한 음식 개념 |
| `DISH_RELATION` | `IS_A`, `VARIANT_OF`, `SIMILAR_TO` 등 음식 간 관계 |
| `CONCEPT_CLAIM` | 핵심 재료, 맛, 식감, 조리법, 식단·알레르기 주장 |
| `KNOWLEDGE_DOCUMENT` | Markdown 형태의 상세 음식 설명과 버전 |
| `KNOWLEDGE_CHUNK` | 설명 facet별 passage, metadata, embedding |
| `MENU_CONCEPT_MAP` | 실제 판매 메뉴와 음식 개념의 연결 및 매핑 상태 |
| `MERCHANT_ORIGIN_DECLARATION` | 가게 원산지 원문, 출처, 버전, 수집일 |
| `MERCHANT_INGREDIENT` | 가게 범위에서 사용이 확인된 재료 |

기존 `INGREDIENT`, `MENU_INGREDIENT`, `ALLERGEN`, `MENU_ALLERGEN`, `MENU_DIETARY_ATTRIBUTE`, `OPTION_DIETARY_CONFLICT`, `EVIDENCE`는 유지·확장한다. 현재 `MENU_KNOWLEDGE`도 즉시 삭제하지 않고 새 지식 문서 구조로 마이그레이션하거나 호환 뷰를 제공한다.

### 7.4 음식 개념 그래프와 관계

예시 관계는 다음과 같다.

```text
중식 → 짜장면 → 쟁반짜장
김밥 → 참치김밥
김밥 → 치즈김밥
```

관계 유형 예시:

- `IS_A`: 참치김밥은 김밥의 한 종류
- `VARIANT_OF`: 쟁반짜장은 짜장면의 변형
- `TYPICALLY_CONTAINS`: 일반적으로 사용하는 재료
- `MAY_CONTAIN`: 변형에 따라 들어갈 수 있는 재료
- `CONFIRMED_CONTAINS`: 특정 메뉴에서 확인된 재료
- `OPTION_ADDS`: 옵션이 추가하는 재료
- `OPTION_REMOVES`: 옵션이 제거하는 재료
- `EVIDENCED_BY`: 주장을 뒷받침하는 근거
- `SERVED_AS`: 음식 개념과 실제 판매 메뉴 연결

초기 데모에서는 별도 Graph DB를 도입하지 않는다. Oracle 관계형 테이블과 관계 edge로 시작하고, 복잡한 경로 질의가 실제로 필요해지면 동일 테이블 위에 Oracle SQL Property Graph 적용을 검토한다.

### 7.5 Wiki 재료 주장 등급

Wiki의 일반적인 재료 지식은 단순 참고 정보가 아니라 실제 후보 필터링에 사용하는 **기본 재료 모델**이다. 각 음식 개념의 재료에는 다음 역할 등급을 부여한다.

| 역할 | 의미 | 기본 판정 |
|---|---|---|
| `DEFINING` | 이 재료가 없으면 사실상 다른 메뉴가 됨 | 충돌 시 기본 제외 |
| `CORE` | 거의 대부분의 일반적 조리법에 사용 | 충돌 시 기본 제외 |
| `COMMON` | 자주 사용하지만 가게별 차이가 있음 | 엄격한 제약이면 제외, 아니면 경고·감점 |
| `OPTIONAL` | 선택·토핑·변형에 따라 사용 | 옵션 확인 또는 경고 |
| `REGIONAL_VARIANT` | 지역·조리 방식에 따라 사용 | 해당 변형에만 적용 |
| `UNKNOWN` | 충분한 근거가 없음 | 안전하다고 판정하지 않음 |

재료 역할과 실제 메뉴의 주장 상태는 별도로 관리한다.

```text
CONFIRMED_PRESENT
CONFIRMED_ABSENT
PRESUMED_PRESENT
POSSIBLE
UNKNOWN
CONFLICTING
```

통계 근거가 없는 `95%` 같은 정밀 확률은 사용하지 않는다. 역할 등급, 출처, 적용 범위, 변형 정보를 명시한다.

### 7.6 상속과 구체적 근거의 덮어쓰기

실제 메뉴의 유효 재료는 다음 순서로 계산한다.

```text
음식 Wiki에서 상속한 DEFINING·CORE 재료
+ Wiki의 COMMON·OPTIONAL 위험
+ 가게·메뉴별 확인된 추가 재료
- 메뉴별로 명시적으로 제거된 재료
+ 사용자가 선택한 옵션의 추가·제거 효과
```

핵심 규칙:

1. `DEFINING`과 `CORE`는 매핑된 실제 메뉴에 `PRESUMED_PRESENT`로 상속한다.
2. 특정 메뉴의 신뢰 가능한 공식 사실은 범용 Wiki 주장보다 우선한다.
3. 적용 범위가 명확한 특정 메뉴의 `CONFIRMED_ABSENT` 또는 검증된 옵션 제거 사실만 상속 재료를 제거할 수 있다.
4. 가게 전체 원산지 정보는 `가게가 사용함`을 증명하지만 개별 메뉴 포함을 자동 확정하지 않는다.
5. 옵션은 기본 메뉴 판정 후 마지막에 적용하고 최종 후보를 다시 검증한다.
6. Wiki에 재료가 없다는 사실은 `CONFIRMED_ABSENT`가 아니다.
7. 교차접촉은 재료 포함 여부와 별도 축으로 판정한다.

이는 위험 발견과 안전 보증을 비대칭으로 처리하는 정책이다. Wiki의 핵심 재료는 충돌 후보를 선제적으로 제외하는 강한 근거지만, Wiki에 없는 재료의 부재를 보증하지는 않는다.

### 7.7 제약 엄격도별 적용

| 사용자 제약 | Wiki `DEFINING`·`CORE` | `COMMON` | Wiki에 미기재 | 특정 메뉴 근거 |
|---|---|---|---|---|
| 단순 취향 | 제외 | 감점·경고 | 허용 가능 | 있으면 우선 적용 |
| 엄격한 종교·식단 | 제외 | 기본 제외 | 불확실성 표시 | 확인 근거로 보강·수정 |
| 심각한 알레르기 | 제외 | 보수적으로 제외 | 안전으로 간주하지 않음 | 재료와 교차접촉을 별도 확인 |

프로필의 `allergy_severity`, 식단 규칙, 대화에서 표현한 `절대`, `선호하지 않음` 등의 의미를 구조화하여 적용한다. 필요할 때만 사용자의 제약 엄격도를 짧게 확인한다.

### 7.8 가공 재료와 알레르기 관계

직접 재료만 저장해서는 충분하지 않다. 다음과 같은 하위 관계를 표현한다.

```text
치즈 → 우유
마요네즈 → 달걀 가능성
어묵 → 생선 + 밀 가능성
고추장 → 대두 + 밀 가능성
육수 → 고기·생선·조개류 변형 가능성
```

제품과 제조사에 따라 달라지는 성분은 `CONFIRMED`로 승격하지 않고 `COMMON` 또는 `POSSIBLE`로 유지한다. 소스와 가공품은 브랜드·사양이 확인된 경우에만 메뉴별 사실로 확정한다.

### 7.9 원산지 정보 정규화 예시

가게 원산지 원문이 다음과 같다고 가정한다.

```text
돼지고기(국내산): 짜장면, 쟁반짜장
오징어(원양산): 쟁반짜장
쌀(국내산)
```

정규화 결과:

- 짜장면 메뉴의 돼지고기: `CONFIRMED_PRESENT`
- 쟁반짜장 메뉴의 돼지고기·오징어: `CONFIRMED_PRESENT`
- 가게의 쌀 사용: `CONFIRMED_PRESENT`
- 메뉴가 명시되지 않은 다른 메뉴의 돼지고기·쌀 포함 여부: `UNKNOWN`

목업 데이터는 모두 `SYNTHETIC_MERCHANT_ORIGIN_DECLARATION`으로 표시하고, 실제 요기요 제공 정보로 오인되지 않게 한다.

### 7.10 하이브리드 추천·설명 파이프라인

```text
자연스러운 다중 턴 대화
→ MealNeedState와 DialogueAct 갱신
→ readiness gate
→ 배달 가능 지역·가용성·가격 SQL 필터
→ 실제 메뉴와 DISH_CONCEPT 매핑
→ Wiki 핵심 재료 상속 및 하드 제약 필터
→ 메뉴·원산지·옵션 근거로 보강·수정
→ lexical/vector로 관련 설명과 취향 적합성 검색
→ 규칙 기반 안전·식단 재검증
→ 취향·실용 조건 기반 재랭킹
→ 동일 RecommendationResult로 본문과 카드 생성
```

사용자가 `떡볶이가 뭐야?`처럼 음식 설명만 요청하는 경우 readiness gate를 통과하지 않아도 설명할 수 있다. 단, 실제 메뉴 추천 카드는 생성하지 않는다.

LLM은 검색된 문서를 보고 후보를 임의로 고르는 주체가 아니다. 서버가 결정한 후보와 근거를 자연스럽게 설명하고, 부족한 정보를 질문하며, 사용자가 이해하기 쉬운 표현으로 비교한다.

### 7.11 사용자 노출 문구 계약

근거 범위를 문장에 반영한다.

- Wiki 일반 지식: `이 음식에는 보통 ...이 사용돼요.`
- 메뉴별 확인 정보: `가게가 공개한 정보상 이 메뉴에는 ...이 사용됩니다.`
- 가능성: `조리법에 따라 ...이 들어갈 수 있어요.`
- 미확인: `이 메뉴의 ... 포함 여부는 확인되지 않았습니다.`
- 교차접촉: `재료 목록과 별개로 조리 과정의 교차접촉 여부는 확인되지 않았습니다.`

`안전합니다`, `알레르기 걱정이 없습니다`, `할랄입니다` 같은 강한 표현은 해당 범위의 검증 근거와 정책 조건이 모두 충족될 때만 허용한다.

### 7.12 데모 데이터 범위

현재 150개 실제 메뉴마다 독립된 장문 Wiki를 만들지 않는다.

1. 현재 20개 음식군을 `DISH_CONCEPT` 상위 노드로 구성한다.
2. 현재 34개 고유 설명 패턴을 출발점으로 세부 변형 노드를 설계한다.
3. 150개 메뉴를 모두 음식 개념에 매핑하거나 `UNMAPPED`로 명시한다.
4. 음식군·변형 Wiki는 재사용하고, 가격·가용성·원산지·개별 재료·옵션만 메뉴별로 둔다.
5. 대표 시나리오 8~10개는 최고 품질의 golden slice로 먼저 완성한 뒤 전체 범위로 확장한다.
6. 문서와 사실은 모두 합성 데모 데이터로 표시한다.

AI는 조사 초안, 구조화, 관계 생성, 모순 탐지, 테스트 생성을 지원할 수 있다. 그러나 실서비스에서 안전 관련 주장을 `검증됨`으로 표시하려면 가게 제공 정보, 신뢰 가능한 출처 또는 도메인 검토가 필요하다.

## 8. 개선 원칙

1. **추천 전에 이해한다.** 정보가 부족하면 카드를 만들지 않고 질문한다.
2. **LLM이 추천 가능 여부를 단독 결정하지 않는다.** 서버 정책과 readiness gate가 결정한다.
3. **하드 제약은 Vector Search보다 먼저 적용한다.** 알레르기, 제외 재료, 예산, 서비스 지역은 구조화된 필터다.
4. **부정 조건을 별도 상태로 저장한다.** `no soup`를 단순 임베딩 문장으로 처리하지 않는다.
5. **본문과 카드가 하나의 추천 결과를 공유한다.** LLM이 별도로 후보를 재해석하거나 추가하지 않는다.
6. **근거 없는 사실은 생성하지 않는다.** 재료·가격·식이·옵션·배달 정보는 서버 데이터만 사용한다.
7. **fallback은 현재 대화 행위를 보존한다.** 오류가 곧 메뉴 추천을 의미하지 않는다.
8. **데이터 품질을 확보한 뒤 규모를 늘린다.** 검토된 음식 개념과 정확한 메뉴 매핑이 템플릿 메뉴 수백 개보다 낫다.
9. **평가는 실제 대화 단위로 한다.** 단일 검색 쿼리 점수만으로 챗봇 품질을 선언하지 않는다.
10. **합성 데이터와 Mock 경계는 계속 명확히 유지한다.** 실제 요기요·결제·주문 연동으로 표현하지 않는다.
11. **Wiki 핵심 재료를 기본 재료 모델로 사용한다.** `DEFINING`·`CORE` 충돌은 선제적으로 필터링한다.
12. **존재 추정과 부재 보증을 구분한다.** Wiki에 없는 재료를 실제 메뉴에도 없다고 단정하지 않는다.
13. **더 구체적인 사실이 일반 지식을 덮어쓴다.** 메뉴·원산지·옵션의 명시적 근거를 우선한다.
14. **데모 추천에서 리뷰 가중치는 0이다.** 리뷰는 삭제하지 않고 차후 검증된 약한 신호로만 재도입한다.
15. **Markdown과 DB를 함께 사용한다.** Markdown은 편집 원본, Oracle은 구조화된 런타임 정본이다.

## 9. 권장 구현 순서

### Phase 0. 대화 계약과 평가셋 정의

먼저 원하는 사용자 경험을 테스트 가능한 계약으로 바꾼다.

필수 산출물:

- `DialogueAct` 정의
- `MealNeedState` 정의
- 추천 readiness 규칙
- 음식 개념·재료 역할·주장 상태 계약
- 상속·덮어쓰기·교차접촉 정책
- 다중 턴 golden transcript
- 지식·안전 golden case
- 제품 품질 지표와 회귀 기준

권장 대화 행위:

```text
GREET
ASK_CLARIFYING
CONFIRM_NEEDS
RECOMMEND
EXPLAIN
COMPARE
REVISE
OUT_OF_SCOPE
```

권장 니즈 상태:

```text
stage
occasion
party_size
appetite
staple_preferences
temperature
textures
flavors
budget
spice_tolerance
dietary_constraints
excluded_ingredients
excluded_forms
positive_preferences
negative_preferences
shown_menu_ids
rejected_menu_ids
selected_menu_id
missing_fields
recommendation_readiness
```

### Phase 1. 대화 상태 엔진과 추천 gate 구현

- 사용자 메시지에서 구조화된 `PreferenceDelta` 추출
- 기존 `MealNeedState`와 안전하게 병합
- 정정과 부정 조건을 이전 값보다 우선 적용
- 가장 정보 가치가 높은 질문 하나 선택
- 정보가 충분하거나 사용자가 즉시 추천을 명시했을 때만 `RECOMMEND` 허용
- 도구 없는 정상 인사·질문·요약 응답 허용
- 세션 상태와 required slot을 Oracle에 실제 저장

### Phase 2. 오케스트레이션과 UI-서버 계약 정비

- 마지막 문장 키워드가 아니라 `DialogueAct + State`로 도구 선택
- assistant turn 전체와 추천 snapshot 저장
- 카드 선택·거절·비교 이벤트를 서버에 전달
- 본문과 카드가 동일한 `RecommendationResult`를 사용
- 상태별 deterministic fallback 구현
- 오류 유형별 안전 코드와 운영 지표 기록

### Phase 3. 메뉴 지식 그래프 스키마와 authoring pipeline

- `DISH_CONCEPT`, `DISH_RELATION`, `CONCEPT_CLAIM`, `KNOWLEDGE_DOCUMENT`, `KNOWLEDGE_CHUNK`, `MENU_CONCEPT_MAP` 설계
- `MERCHANT.origin_info_raw`, `MERCHANT_ORIGIN_DECLARATION`, `MERCHANT_INGREDIENT` 설계
- 기존 정규화 재료·알레르기·옵션 테이블과 연결
- Markdown front matter 및 본문 템플릿 정의
- Markdown 검증, 정규화, chunking, embedding, 적재 흐름 구현
- source/version 변경 시 embedding과 설명 cache 무효화
- 기존 `MENU_KNOWLEDGE` 호환 및 마이그레이션 경로 마련

### Phase 4. 고품질 합성 Wiki·가게·메뉴 데이터 정비

우선 정규화할 데이터:

- 음식군·세부 변형과 관계
- `DEFINING`, `CORE`, `COMMON`, `OPTIONAL` 재료
- 소스·육수·가공품과 하위 알레르기 관계
- 고기·해산물·유제품 등 제외 조건
- 조리 형태: 국물, 볶음, 튀김, 구이
- 주식: 밥, 면, 떡, 빵
- 온도, 맛, 식감, 포만감
- 인분과 식사/간식 구분
- 옵션 선택에 따른 성분 변화
- 가게별 원산지 원문과 정규화된 재료 범위
- 주소별 서비스 지역
- 근거 출처, 적용 범위, 확신도, 유효기간
- 음식 설명용 고품질 Markdown passage

리뷰는 추천 데이터셋에서 제외한다. 20개 음식군과 대표 변형의 golden slice를 먼저 완성한 뒤 150개 메뉴 전체를 매핑한다.

### Phase 5. 하이브리드 추천·검색·RAG 개선

권장 파이프라인:

```text
누적 MealNeedState
→ SQL 하드 필터
→ 음식 개념 매핑 및 Wiki 핵심 재료 상속
→ 메뉴·원산지·옵션 근거 병합
→ 하드 제약 선제 필터
→ lexical/vector 설명·취향 후보 검색
→ 규칙 기반 식이·근거 재검증
→ 취향·실용 조건 기반 재랭킹
→ 후보 다양성 조정
→ 점수/준비도 미달 시 추가 질문
→ Top 후보 추천
```

세부 원칙:

- 부정 조건을 명시적 필터로 처리
- 검색 쿼리는 마지막 발화가 아니라 누적 니즈 상태에서 생성
- 후보 전체에 하드 필터를 마지막으로 한 번 더 적용
- 추천 이유는 서버의 필드별 매칭 결과로 생성
- Top 후보에 대해서만 관련 Wiki·근거 passage 검색
- 실제 근거 passage를 제한된 형태로 LLM에 전달
- 리뷰 유사도와 추천 가중치는 `0`으로 유지
- Wiki `DEFINING`·`CORE` 충돌은 기본 제외
- Wiki에 미기재된 재료는 `CONFIRMED_ABSENT`로 해석하지 않음
- 메뉴별 명시적 근거와 옵션 변경을 적용한 뒤 최종 재검증
- 데이터 품질 확보 후 OCI 임베딩 도입 여부 판단
- 검색 점수가 낮거나 후보가 서로 비슷하면 추천 대신 질문

### Phase 6. 프롬프트와 LLM 응답 계약 개선

프롬프트에는 다음을 명시적으로 전달한다.

- 현재 `DialogueAct`
- 누적된 사용자 니즈
- 확정 정보와 추정 정보
- 부족한 정보
- 추천 가능 여부
- 이번 턴에 허용된 행동
- 사용할 수 있는 근거와 금지된 추론
- Wiki 일반 지식과 메뉴별 확인 사실의 범위
- 주장 상태에 맞는 사용자 노출 표현
- 사용자에게 노출하지 않을 내부 ID
- Markdown 사용 여부와 프론트엔드 렌더링 계약

가능하면 자연어만 받지 않고 구조화된 응답을 사용한다.

```json
{
  "dialogue_act": "ASK_CLARIFYING",
  "assistant_text": "Do you feel more like rice, noodles, or something snack-like?",
  "state_delta": {},
  "recommendation_result_id": null
}
```

### Phase 7. 평가·관측·배포

- 실제 다중 턴 회귀 테스트
- Oracle/GenAI 통합 테스트
- provider와 tool 오류 유형별 집계
- fallback율과 원인별 비율 확인
- 외국인 사용자 평가
- Wiki claim과 메뉴 매핑 품질 검토
- 원산지 범위와 옵션 override 회귀 검증
- 기존 주문·안전 회귀 테스트 유지
- 공개 배포 후 동일 transcript 재검증

## 11. 최소 다중 턴·지식 회귀 시나리오

다음 시나리오는 차후 구현의 필수 회귀 기준으로 사용한다.

1. `hi` → 메뉴 없이 인사와 첫 질문
2. `I don't know yet` → 선택하기 쉬운 질문 하나
3. `Ask me questions before recommending` → 추천 보류
4. `Something warm` → 필요한 추가 정보 질문
5. `No soup` → 이후 모든 국물 메뉴 제외
6. `Rice, under 12,000 won, no pork` → 조건 충족 후보만 추천
7. `Actually, noodles are okay, but still no soup` → 정정과 유지 조건 동시 반영
8. `Tell me about the second one` → 직전 snapshot의 두 번째 후보 설명
9. `I don't like those` → 후보 거절 이력 저장 후 다른 방향 질문
10. `Why did you recommend pork?` → 오류 인정, 원인 설명, 즉시 안전하게 재검색
11. 긴 대화 후 초기 알레르기 조건 확인 → 프로필 하드 제약 유지
12. provider 장애 → 현재 DialogueAct를 유지하는 fallback
13. 참치김밥의 `DEFINING` 생선 claim → 생선 제외 사용자에게 기본 제외
14. Wiki의 `CORE` 재료와 충돌 → 메뉴별 근거가 없어도 보수적으로 제외
15. Wiki에 달걀이 미기재됨 → 달걀 부재 또는 안전으로 표시하지 않음
16. 메뉴별 `CONFIRMED_ABSENT` → 범용 Wiki 상속을 해당 메뉴에서만 덮어씀
17. 가게 원산지에 돼지고기만 기재되고 메뉴명이 없음 → 모든 메뉴에 자동 포함하지 않음
18. 원산지에 메뉴명과 재료가 함께 기재됨 → 해당 메뉴에만 `CONFIRMED_PRESENT`
19. 치즈 옵션 추가 → 우유 관련 식단·알레르기 판정 재계산
20. 리뷰에 안전하다는 문장이 있어도 → 추천·안전 판정에 영향 없음
21. `떡볶이가 뭐야?` → 추천 카드 없이 Wiki 기반 음식 설명
22. 음식 설명의 사실 문장 → 관련 claim 또는 passage로 추적 가능

## 12. LangChain·LangGraph·GraphRAG 판단

### 현재 권고

- LangChain으로 즉시 교체하지 않는다.
- 우선 순수 Python, Pydantic, Oracle 상태 테이블로 대화 계약과 상태 엔진을 올바르게 구현한다.
- Function Calling은 현재 OpenAI SDK 기반 루프를 재사용할 수 있다.
- 음식 관계가 그래프라는 이유만으로 별도 Graph DB나 GraphRAG 프레임워크를 도입하지 않는다.
- Oracle 관계형 edge와 Vector Search로 먼저 구현하고, 복잡한 경로 탐색이 실제 필요할 때 SQL Property Graph를 검토한다.

### LangGraph 도입을 검토할 시점

다음 조건이 실제로 발생하면 LangGraph가 유용할 수 있다.

- 상태 분기와 원래 상태 복귀가 복잡해짐
- 장시간 실행과 중단·재개가 필요함
- 단계별 checkpoint와 재시도가 필요함
- 사용자 확인을 기다리는 human-in-the-loop 노드가 많아짐
- 대화 그래프를 시각적으로 추적할 필요가 커짐

LangGraph는 상태형 워크플로와 durable execution을 위한 저수준 오케스트레이션 도구이며 LangChain 없이도 사용할 수 있다. 하지만 프레임워크는 잘못된 데이터, 추천 정책, 평가 기준을 대신 설계해 주지 않는다. 따라서 Phase 0~2의 계약이 안정된 뒤 도입 효과를 평가한다.

- <https://docs.langchain.com/oss/python/langgraph/graph-api>
- <https://docs.langchain.com/oss/python/langchain/agents>

## 13. 다음 권장 마일스톤

첫 구현 마일스톤은 다음 범위로 제한하는 것이 좋다.

> `MealNeedState + DialogueAct + 추천 readiness gate + 상태별 fallback + 12개 다중 턴 회귀 시나리오`

이 단계의 완료 기준은 다음과 같다.

- `hi`에서 메뉴 카드가 나오지 않는다.
- 사용자가 질문을 요청하면 최소 한 번 이상 니즈 질문을 수행한다.
- 사용자가 추천 보류를 요청하면 카드를 만들지 않는다.
- `no soup`, `no pork` 같은 조건이 다음 턴에도 유지된다.
- 추천 시점과 추천 이유를 서버 상태로 설명할 수 있다.
- provider 장애가 발생해도 현재 대화 의도에 맞는 fallback을 반환한다.
- 기존 식이 안전·장바구니·Mock 주문 회귀 테스트는 계속 통과한다.

이 기반이 완성된 후 DB 구조·합성 데이터·검색·RAG·프롬프트를 순차적으로 개선한다.

두 번째 구현 마일스톤은 다음 범위로 한다.

> `음식 개념·재료 claim 계약 + Markdown authoring pipeline + 8~10개 golden Wiki + 원산지 정규화 + Wiki 상속 기반 제약 필터`

두 번째 마일스톤의 완료 기준:

- 대표 음식 Wiki가 설명·맛·식감·문화·핵심 재료·변형 정보를 포함한다.
- `DEFINING`, `CORE`, `COMMON`, `OPTIONAL` 등급이 출처와 함께 저장된다.
- 대표 메뉴가 음식 개념에 매핑되고 핵심 재료를 상속한다.
- Wiki 핵심 재료 충돌이 추천 전에 제외된다.
- Wiki 미기재 재료를 안전 또는 부재로 오판하지 않는다.
- 가게 원산지 원문과 정규화된 적용 범위가 함께 보존된다.
- 메뉴별 사실과 옵션이 범용 Wiki 기본값을 올바르게 수정한다.
- 리뷰 가중치가 0이며 추천·안전 컨텍스트에 들어가지 않는다.
- 음식 설명 문장이 실제 Wiki passage와 claim을 근거로 생성된다.
